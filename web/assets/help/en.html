m-ui HelpReseller panel help

Find a feature in the contents (on a phone, tap “Contents” at the top right), or use the search box above. Text in grey boxes matches the buttons and titles in the panel exactly, so you can look for it and click it. This view only covers what the reseller panel can do.

Getting started

m-ui is a self-hosted proxy panel: lines, users, subscriptions, certificates, backups and multiple servers, all managed in the browser.

The reseller panel manages the users under your account: create them, renew them, watch their usage, and send them their subscription links.

A few words first

These ideas come up everywhere in the panel; knowing them makes the rest easy.

  • Line: the entry clients connect to, a protocol plus a port, and where its traffic leaves from. The nodes in a user's subscription are generated from lines.
  • Upstream: the exit of a line. The default is direct (straight out of this server); it can also be WARP or another exit server.
  • User: one subscription link with a traffic quota, expiry, device limit and speed limit; it is disabled automatically when it runs over.
  • Plan: a template of quota, duration, devices, speed and lines, applied in one click when creating or renewing a user.
  • Subscription: the link clients import; opened in a browser, the same link shows the user's own landing page.
  • Master / node servers: the master holds all data and does the accounting; nodes only forward traffic and get their configuration from the master.
  • Reseller: someone who sells accounts for the site owner and only manages their own users in their own reseller panel.

First sign-in

Open the panel in a browser after installing, and change the default password first.

  1. Open http://SERVER-IP:2053/app/ (use the port and path printed at the end of the installation).
  2. Sign in with the default account admin / admin.
  3. A red bar at the top warns about the default password. Click Change now; on the Admin page, under Login account, fill in Current password and New password, click Update account, then sign in again with the new password.
Common pitfalls
  • Opening just http://SERVER-IP:2053/ gives a 404 on purpose: the panel path is not revealed to port scanners. Always include the full path.
  • The page does not load: check that the cloud security group / firewall allows 2053/tcp.
  • Forgot the address or password: SSH into the server and run m-ui; option 1 shows the panel address, option 5 resets the admin password.

Five steps to go live

The Quick start checklist on the dashboard is exactly these steps; after the first four you can hand out accounts.

  1. Change the default password (see above).
  2. Get a certificate: Certificate page → Add a certificate. With a domain, choose Domain (auto-issue); without one, choose No domain (self-signed) and click Generate self-signed. See Certificates.
  3. Create a line: Lines page → Quick add; beginners pick Hysteria2 or AnyTLS and save. See Lines and protocols.
  4. Create a user: Users page → Add user; fill in a name and the quota, tick the Lines they may use, save.
  5. Send the subscription: click the user's name to open the details, copy the subscription link and send it, or let them scan the QR code. Opened in a browser, the link offers one-tap import into their app.
No domain? No problemA self-signed certificate plus the server IP works: subscriptions tell clients to allow the insecure certificate automatically, so users change no settings. Issue a real certificate later when you have a domain; users just refresh their subscription once.
Common pitfallOpen each line's port in the cloud security group and the system firewall: Hysteria2 and TUIC use UDP, most others use TCP. A closed port is the most common reason for "cannot connect".

Reseller: three steps to start

Once the site owner has created your reseller account, these three steps get you selling.

  1. Open the reseller panel address you were given (default port 2054, path /dl/). Enter your reseller name as the username; on the first sign-in leave the password empty and click Sign in, then set a password when asked. See First sign-in and password.
  2. (Optional) Create a few plans on the Plans page so new accounts and renewals take one click.
  3. On the Users page click Add user: enter a name, choose a plan or fill in the quota, tick the Lines, save. Click the user's name to open the details and send them the subscription link.
The reseller panel has four pagesDashboard, Users, Plans and Account. You only see your own users and the plans you created.

Finding your way around

Navigation is on the left, help and feedback are at the top right, and coloured bars at the top of the page are reminders that need your attention.

  • The navigation, top to bottom: Dashboard, Lines, Upstreams, External nodes, Users, Resellers, Plans, Rules, Servers, Certificate, Backup, Ops, Logs, Admin, Settings.
  • Bottom left: theme (◐ follow the system, ☀ light, ☾ dark), language and Sign out. An arrow next to the version number means an update is available; click it to update (see Updating).
  • Top right: Help (this page) and Feedback / Support (contact the author, report problems).
  • Reminder bars at the top: default password still in use, certificates need attention, mainland reachability problems, a failed data-plane reload and so on. Follow the hint; bars that can be dismissed have Got it.
  • On a node server's own panel, pages such as lines and users are read-only; make changes on the master.
  • Shortcuts: / jumps to the page's search box, Esc closes dialogs, Ctrl + Enter submits a dialog. On a phone, tap ☰ at the top left to open the navigation.

Servers: master and nodes

One master server holds all the data; any number of node servers can be added as extra entry points. Each line appears once per server in subscriptions, and clients pick the fastest.

Do I need nodes?

One server is enough to start; add nodes when you want more regions or more entry points.

  • Every 5 seconds the master pushes lines and users to the nodes and collects their traffic and online devices; quotas and expiry are judged on the master only.
  • Nodes only forward traffic. If the master is unreachable for a while, nodes keep serving with the last configuration they got; traffic is reconciled afterwards and never billed twice.
  • Add a server and every user's subscription gains the matching nodes automatically.

Attach a node

Install m-ui on the node and enter its pairing details on the master.

  1. Install m-ui on the node server the same way and sign in to its panel (change the default password first).
  2. On the node: Settings → Role, tick Run as node (secondary server) and click Save.
  3. On the node: Settings → Pairing, copy the API URL and the Pairing token.
  4. On the master: Servers page → Add server. Enter a Name (it becomes the suffix of node names in subscriptions, such as "HK"), the API URL and the pairing token. If the node's panel uses a self-signed certificate or a bare IP, tick Skip certificate verification.
  5. A few seconds after saving the row should show synced.
Common pitfalls
  • With an http:// API URL the token and every user's credentials travel in plain text; the row is marked Plaintext. Give the node's panel HTTPS (self-signed is fine), or allow its panel port only from the master's IP.
  • Each node issues and renews its own certificates on its own Certificate page.
  • On a node's panel, lines, users and plans are read-only; make changes on the master.
  • Keep master and nodes on the same version: when a row says version differs from master, update the node.

Connect address, IPv4 and IPv6

By default subscriptions use each server's detected public IP, with the domain used only as SNI, so a poisoned DNS on the client cannot break the connection.

  • Edit a server → Connect address (IP allowed): leave it empty to use the detected public IP, or enter a fixed IP or domain.
  • Auto address uses: dual-stack servers give IPv4 by default and can switch to IPv6; if the chosen family was not detected, the other one is used. A manual connect address ignores this setting.
  • On dual-stack servers each line can also pick its own IP version in the line form.
  • To put the domain instead of the IP into subscriptions: Settings → Subscription → Node address in subscriptions, choose domain.
IPv6 inbound checkWhen a server uses IPv6 by default, or a line is set to IPv6 on it, the master checks from outside whether its IPv6 ports can be reached and shows the result on the Servers page. "Unreachable" usually means the security group does not allow ::/0 or the server's own firewall blocks IPv6. UDP lines (hysteria2, tuic) cannot be checked this way; capture packets on the server to confirm.
IPv6 pitfalls
  • Cloud IPv6 needs its own security-group rules for ::/0 (separate TCP and UDP rules); ip6tables / ufw on the server must allow it too. Flushing iptables does not open IPv6.
  • Outbound-only IPv6 (WARP, NAT and the like) cannot be used by clients to connect.
  • IPv6-only servers: install WARP before checking for updates (see WARP). Direct exits cannot reach IPv4-only sites; choose warp as the line's upstream to reach the whole internet.

Traffic ratio

Charge more for an expensive server: traffic through it counts towards users' quotas with a multiplier.

  • Edit a server → Traffic ratio: 2 counts double and adds an x2 tag to node names; 1 counts as is. The master can have a ratio too.
  • Users' usage, the chart in their details and the numbers on their landing page all use the converted figures, so they add up; line and upstream statistics show actual traffic.

Mainland reachability

Find out whether a server is blocked in mainland China: home-broadband probes of China Mobile, China Telecom and China Unicom connect to it, with Hong Kong probes as a control.

  • The Mainland reach column on the Servers page shows the result. Click a cell for details, or Check mainland reach to test every server.
  • Reading the result: OK; Partly down (one carrier cannot connect); Likely blocked; IP blocked (change the IP); Port blocked (change the port); Down abroad too (a server, port or security-group problem, not a block).
  • Scheduled checks: Settings → Mainland reachability → Automatic checks (every 90 minutes by default), with a Telegram alert when a server gets blocked or recovers.
Common pitfalls
  • The server address is sent to the public Globalping network. Without an account you get about 250 probe runs per hour and one server uses about 15; if that is not enough, add a free Globalping token (optional) in the settings.
  • The check uses the port of the server's first TCP line; with only hysteria2 / tuic (UDP) lines it can only tell whether the IP is blocked. Only IPv4 is checked for now.

Disabling, deleting and offline nodes

Disabling or deleting a node stops it serving right away; when a node shows offline, start with the reason shown in its row.

  • Edit a server and untick Enabled: it immediately stops serving everyone; enable it again to resume.
  • Deleting a server disables lines that were deployed only there, and users or resellers that only used it lose that line; the affected lines and people are listed afterwards.
  • shutdown notice pending: that machine has not yet received the notice to stop serving; the master keeps retrying. To stop it at once, turn off node mode on that machine or uninstall m-ui there.
  • Offline reasons: connection timed out, connection refused (port not open or panel not running), DNS lookup failed, certificate not trusted (tick skip certificate verification), token mismatch (copy the pairing token again), Certificate fingerprint changed (if you really re-issued the node's certificate, click Reset fingerprint).
  • Replacing a node: install the new one, then edit the old row on the Servers page with the new API URL and token; the master pushes everything again.

Master failover

If the master's VPS goes down or is deleted by mistake, a node near the top of the server list can take over as a temporary master; later the data moves back to a new master. Off by default.

How it works

The master regularly sends an encrypted full copy of its data, only to the first few nodes in server order (the candidates).

  • 2 candidates by default (1–3 allowed), taken in the order of the Servers page; a candidate's API URL must be HTTPS.
  • A copy is sent every 5 minutes by default and again shortly after changes; it stays encrypted until a takeover.
  • While the master is unreachable, nodes keep forwarding and users notice nothing; a takeover restores management, accounting, subscriptions and alerts.
  • After a takeover, node traffic is reconciled automatically; management changes made on the old master after the last copy (new users, for example) must be redone.

Takeover modes

Choose a takeover mode when you turn failover on: the more automatic, the less work, and the more care is needed against false alarms.

  • Manual: when the master is lost, the candidate sends a Telegram alert; you take over from the candidate's panel, or over SSH with the m-ui command line.
  • Telegram confirmation: after the master has been gone for the set number of minutes, the bot sends a confirmation code, and the takeover happens only after you reply.
  • Fully automatic: takes over once the master has been gone for the set time. With just one master and one node an outside witness (Globalping) must be on, so a broken link between the two alone does not trigger a takeover.
  • When the takeover is done, Telegram sends the temporary master's panel address; accounts, passwords and 2FA are the same as on the old master, and everyone signs in again.
Common pitfalls
  • Do not take over by hand while the master is merely updating or restarting; it is back in a few minutes.
  • If the subscription address points at the old master, users cannot refresh their subscriptions after a takeover (nodes already imported keep working). Use a separate subscription domain with a short TTL and point it at the temporary master after a takeover, or turn on the Cloudflare option below.

When the old master comes back

The old master does not fight the temporary master: it automatically becomes a read-only node.

  • It changes no data from then on; changes it received after the takeover are kept aside so you can compare and redo them.
  • To make it the master again, move the data back from the temporary master as described next.

Moving back to a new master

The temporary master is only a bridge: once the data is moved to a new master it returns to being a node. The new master can be the demoted old master or a fresh VPS with m-ui installed.

  • Working on the new master: generate a one-time move-back code in the temporary master's panel, then enter the temporary master's address and the code in the new master's panel.
  • Working on the temporary master: generate a one-time receive code in the new master's panel, then enter the new master's address and the code in the temporary master's panel.
  • You can keep the old master's identity (ports, paths, domain and certificates stay the same, so subscription links are unchanged once DNS points back), or use the new master's own settings (subscription links change).
  • During the move the temporary master briefly freezes management changes, then unfreezes and turns back into a node.
Common pitfallMove-back and receive codes work once and expire quickly. They are only shown in the panel; never post them in a group chat.

Automatic Cloudflare DNS (optional)

If your domain is on Cloudflare, takeovers and move-backs can update the DNS records to the new machine automatically. Off by default.

  • Needs a Cloudflare API token with DNS edit permission.
  • Only records that currently point to the old master's IP are changed.
  • Without it, update DNS yourself after a takeover or move-back, following the Telegram message.

Lines and protocols

A line decides how clients connect: inbound protocol + port → where the traffic leaves. Each line appears once for every server it is deployed on.

Create a line

Quick add is the easiest start: the protocol settings are ready and a free port is picked for you.

  1. On the Lines page, click Quick add at the top right and pick a preset: Hysteria2, AnyTLS, VLESS + Reality, Trojan, Shadowsocks 2022 or VMess + WS.
  2. The form is filled in; check the Name (the node name shown in subscriptions) and the Port, then save.
  3. To configure everything yourself, click Add line: choose the Protocol and a port; the Upstream defaults to direct (straight out of this server).
  • New lines have Assign to all existing users (not resellers' users) ticked. If you untick it, the line only shows up in subscriptions after you tick it for each user.
  • A free five-digit port is filled in for you and can be changed; a clash with the panel or subscription ports, or with another program on the server, is rejected when you save.
  • Before saving, the whole configuration is test-run by the core; if it fails nothing changes and running lines are untouched. Changing a line restarts the data plane briefly, and online users reconnect by themselves.
Common pitfallOpen the port in the security group / firewall; for UDP protocols (Hysteria2, TUIC) open UDP.

Choosing a protocol

Not sure? Use Hysteria2 as the main line and add one TCP line (AnyTLS or VLESS + Reality) as a backup.

TLS: node certificate, Reality or none

TLS mode decides how the node encrypts and disguises itself; Hysteria2, TUIC and AnyTLS always need TLS.

  • Node certificate: uses a certificate on the server and clients verify the domain. Each server's default certificate is used unless you pick one for this line under Certificate.
  • Reality: no certificate; it imitates the TLS of the site in Handshake target (masquerade domain). Check tests whether that site works; Suggest tests a list of popular sites and ranks them by latency, one click fills one in. Next to Private key click Generate keypair; next to Short ID click Generate.
  • None: plain text, only for CDN origins or internal networks.
  • Leave Client fingerprint at the default unless you know you need another.
Common pitfalls
  • A Reality handshake target must support TLS 1.3 and H2 and be reachable from the server; when the line runs on another server, the measured latency is only a hint.
  • With a self-signed certificate clients must allow insecure certificates. Subscriptions add this automatically (the setting is Allow insecure certificate in subscriptions).

Transport

Only VLESS, VMess and Trojan have a Transport choice; if unsure keep the default TCP (direct).

  • TCP (direct): the fastest.
  • ws, httpupgrade: can go through a CDN.
  • grpc: pairs well with Reality.
  • For VLESS, tick Enable XTLS Vision (TCP + TLS only, recommended).

Hysteria2 port hopping and masquerade

Use port hopping when your ISP throttles single UDP ports; use a masquerade site so probes do not reveal a proxy.

  • Port hopping range: such as 20000-30000. The server forwards that whole UDP range to the line's port and clients hop between ports at random. Open the whole UDP range in the security group / firewall; leave it empty to turn hopping off.
  • Masquerade site: anyone probing the port sees this website instead of a proxy error. Enter a full URL; new lines default to https://www.bing.com. Empty = no masquerade.
  • Up Mbps (0 = unlimited) / Down Mbps (0 = unlimited): usually leave at 0.
  • Obfs password (salamander; empty = off): usually empty; if you set one, subscriptions pass it to clients automatically.

Which servers run a line

With several servers, a line can run on only some of them.

  • Deploy on servers: nothing ticked = all servers (the default); tick servers to run the line only there, and subscriptions only list those entries.
  • Dual-stack servers get an extra drop-down in their row, so the line can use IPv4 or IPv6 on that server (the default follows the Servers page).
  • A line on several servers has several "entries"; when assigning lines to users, plans or resellers you can tick just the entry on one server.

Rule-based routing

Within one line, send chosen sites out through another exit (streaming through an unlocking server, say) or block them.

  1. Edit the line and tick Rule-based routing.
  2. Click + Add rule: choose the Match type (Domain suffix, Full domain, Domain keyword, IP range, Port), enter the values (separate several with commas or new lines) and choose the Egress: direct, an upstream, or Block.
  3. To add by app: type app names (such as douyin, netflix, openai) in the box next to it and click Look up; rules are added for you and you pick the egress in each.
  4. Save.
  • Rules are checked top to bottom and the first match wins; anything unmatched uses the line's own Upstream.
  • An app often uses several domains, so add them together; very short keywords (like ai) catch unrelated sites; traffic to a domain may not match an IP range, so prefer domain rules.
  • Untick Rule-based routing and save to remove all rules.

Batch actions, order and cloning

Tick several lines and a batch bar appears at the top.

  • Enable, Disable, Set upstream, Deploy on (only with several servers), Clear. A batch change reloads the data plane only once.
  • Drag rows to reorder; subscriptions list nodes in the same order.
  • At the end of a row, ⧉ is Clone (a new port is picked) and ⇢ is Add a line as upstream (see Lines as upstreams).

Upstreams and external nodes

Upstreams decide where a line's traffic leaves; external nodes merge nodes from elsewhere into your users' subscriptions.

Add an upstream

An upstream is an exit server: once added, choose it as a line's Upstream and that line's traffic leaves from there.

  1. Upstreams page → Add upstream.
  2. Paste the exit node's share link into Import from share link and click Parse, check the fields and save; or pick the type and fill in the fields yourself.
  3. Click Test to see the latency, then set it as the upstream of a line on the Lines page.
  • VLESS, VMess, Trojan, TUIC, Hysteria2, Shadowsocks and SOCKS exits are supported.
  • An upstream still used by lines cannot be deleted; change those lines' upstream first.

WARP

Cloudflare WARP gives lines a clean exit, often used for streaming or to let IPv6-only servers reach IPv4 sites.

  1. On the Ops page, in the Cloudflare WARP card, click Install, then Enable.
  2. Click Check exit to confirm the exit IP.
  3. If the Upstream row has no warp yet, click Add as upstream "warp".
  4. Choose warp as a line's upstream.
Common pitfallWARP's local port (SOCKS5 port) is 40000 by default and enabling fails if it is taken; after changing the port, enable WARP again. Ops tasks only work on Linux with m-ui running as root.

Lines as upstreams (chaining)

Forward an entry line's traffic into another of your own lines, for example in through a domestic relay and out through an overseas server.

  • On the Upstreams page click Add a line as upstream (or ⇢ at the end of a line's row), then choose the line and Use its entry on server.
  • Its settings follow the line automatically, even if the line changes port or protocol; it uses dedicated credentials, takes nothing from users' quotas, and traffic is counted once.
  • Loops, deleted lines and deleted entry servers are blocked or flagged. Nodes need v0.7.16 or later.

Upstream groups (automatic failover)

Group several upstreams to always use the fastest one that works and switch automatically when it fails.

  • Upstreams page → Add upstream group, pick at least two Members, then choose the group as a line's upstream.
  • Members are tested every 30 seconds; the current one is kept unless it is more than 300 ms slower than the fastest, to avoid flapping. On a switch old connections are closed so apps reconnect at once.
  • The Upstreams page shows which member each server is using now.

Health checks and alerts

Upstreams are tested on a schedule, with optional Telegram alerts on failure and recovery.

  • Each server only tests the upstreams its own lines use; upstreams no line uses are marked Unused and are neither tested nor alerted on.
  • The status column can show Down, Pending or Stale; the arrow at the end of the row shows each server's results and errors.
  • Settings → Upstream health checks: Interval (minutes) (0 = off) and Consecutive failures before alert.
  • The Upstream health card on the dashboard has Check now.

External nodes

Merge nodes from elsewhere (an airport subscription, a single share link) into your users' subscriptions, after your own nodes.

  1. External nodes page → Add external node: choose Subscription (one subscription URL fetched on a schedule) or Share link (a single node).
  2. Fill in Link / subscription URL; a Name prefix (such as "[Relay] ") helps users tell them apart. Save.
  3. On the Users page, edit the users who should get them and tick External nodes.
  • The master fetches them on a schedule set in Settings → Subscription → External subscription refresh interval (minutes); when a fetch fails, the last good content is kept and the error is shown in the list.
  • base64 or plain link lists, Clash YAML and sing-box JSON are supported.

Hide, rename, exclude keywords

Info nodes such as "traffic left" or "website" that airports add, and nodes you do not want to hand out, can be left out.

  • Click Show nodes to see every parsed node; tick some and click Hide selected / Show selected; single nodes can be given a new name with Rename.
  • Hiding and renaming remember both the name and the node's fingerprint (address, port, password and so on), so they survive renames and reordering by the provider.
  • Exclude keywords: nodes whose names contain these words are not output; separate with commas, such as website,expire,traffic left. It also catches nodes that appear later, which suits info nodes whose names change on every refresh.
  • When nodes disappear for a while their hide / rename records are kept and apply again when they return; click Clean up once you are sure they are gone.

Speed tests, mainland checks, use as upstreams

With the nodes shown you can test them right there and turn good ones into upstreams.

  • Test all / Test selected: each enabled server really connects once and measures latency, which tells you how the node works as an upstream; tick with hidden to include hidden nodes; Stop test any time. Unsupported means the protocol cannot be turned into an outbound here and cannot be tested.
  • Test from China: mainland probes of the three carriers connect to the selected nodes to see whether they are blocked; UDP protocols such as hysteria2 and tuic can only be pinged; domestic relay entries failing from Hong Kong is normal.
  • Add as upstreams: tick nodes and give each a name to turn them into upstreams (a duplicate name is an error, nothing is renamed for you).

Certificates

Certificates give lines, the panel and subscriptions TLS / HTTPS. A server can hold several, and issued ones renew automatically.

Add a certificate

Certificate page → Add a certificate, then choose the Certificate source depending on whether you have a domain.

  • Domain (auto-issue): first point the domain's A record to the server IP at your DNS provider. Enter the domain and choose the Validation:
    • HTTP (temporary listener on port 80): port 80 must be free and reachable from the internet.
    • DNS (Cloudflare API): for domains on Cloudflare; enter a Cloudflare API token (with DNS edit permission for the domain; see Creating a Cloudflare API token). Port 80 is not needed and renewal is automatic.
    • DNS (add a TXT record by hand): for other DNS providers; add the TXT records shown, and issuing continues once public DNS sees them.
    Click Pre-check DNS / port first, then Issue certificate. Wildcards (*.example.com) need DNS validation.
  • No domain (self-signed): click Generate self-signed; leave Addresses in the certificate (auto if empty) empty to use the server's public IP. Every node in subscriptions gets "allow insecure" automatically, so clients need no settings; keep the panel and subscriptions on HTTP.
  • Existing certificate: if certbot, aaPanel, nginx or a commercial certificate is already on the server, enter the paths of the Certificate file (fullchain) and the Private key file and click Use this certificate.
Choose what it is forUnder Apply to tick Make it the default for lines, Use for panel HTTPS and / or Use for subscription HTTPS; uses you leave unticked stay as they are.

Creating a Cloudflare API token

Issuing certificates with DNS (Cloudflare API) needs a Cloudflare API token. Let it manage only the DNS of your domain, so a leak cannot touch anything else.

  1. Open Cloudflare's token page with the permissions filled in and sign in to your Cloudflare account. The permissions are already set, "Zone → Zone → Read" and "Zone → DNS → Edit", and the token is named m-ui.
  2. Change "Zone Resources" to "Include → Specific zone → your domain"; do not leave "All zones".
  3. Click "Continue to summary", then "Create Token".
  4. Copy the token shown and paste it into Cloudflare API token on m-ui's Certificate page. It is shown only this once: after you leave the page it cannot be viewed again, and a lost token has to be created anew.
If the link does not open or the page looks different, create it by handIn the Cloudflare dashboard: your avatar at the top right → My Profile → API Tokens → Create Token → the "Edit zone DNS" template → Zone Resources "Include → Specific zone → your domain" → Continue to summary → Create Token. If issuing then says the zone cannot be found, add one more permission to the token: "Zone → Zone → Read".
Common pitfalls
  • Keep it minimal: the two permissions above, on just the domain you use. Do not use the Global API Key, and do not grant account-level permissions.
  • Token leaked? Delete or roll it on the same page and put the new token into m-ui.
  • The automatic DNS update of master failover takes its own token (see Automatic Cloudflare DNS); create another one the same way.

Where certificates are used

Line inbounds, Panel, Subscription and Reseller panel each have their own certificate, changed in the In use card.

  • Click Change next to an item and pick a certificate from the store, or No HTTPS.
  • Subscription changes apply immediately (users need the new https link); a new panel certificate needs Restart m-ui; changing the default line certificate restarts the data plane once.
  • To give one line its own certificate: edit the line → Certificate; servers without that certificate keep using their own default.

Automatic renewal

Issued certificates renew before they expire and are swapped in without a restart.

  • Checked a few minutes after start, then every hour; renewal starts in the last third of the validity period (30 days before expiry for a 90-day certificate).
  • Failures are retried after 1, 2 and 4 hours; the first failure is reported at once, then once a day.
  • The Auto-renew column of the Certificate store shows each certificate's state: last renewal, number of failures and next retry. Click Renew to renew now, or turn auto-renewal off for one certificate.
  • When a certificate needs attention (renewal failing, expiring soon, expired, file unreadable), a "certificates need attention" bar appears at the top; click View to handle it. Node certificates are reported on the master too.
Common pitfalls
  • Certificates issued with DNS (add a TXT record by hand) cannot renew automatically: every renewal needs new TXT records. Re-issue with Cloudflare validation to renew automatically.
  • HTTP validation needs port 80 for a moment on every renewal; a TCP line using port 80 makes renewal fail.
  • An extra AAAA (IPv6) record that does not point to this server makes validation fail: point it here or delete it.
  • Let's Encrypt no longer sends expiry emails: set up Telegram or a webhook at least on the master (see Notifications).
  • An Existing certificate is renewed by the tool that issued it (such as certbot); the panel only reads the files and starts reminding you 14 days before expiry.

Certificates on nodes

Every server manages its own certificates on the Certificate page of its own panel.

  • Certificates are matched by name across servers: if a line picks a certificate, servers without it use their own default; the line's certificate picker shows which servers have it and how many days are left.
  • Nodes usually have no notifications set up, so the master reports their renewal failures and expiries, and the master's Servers page marks cert renewal failing.

Users and plans

A user is one subscription link with a traffic quota, expiry, device limit and speed limit; a plan is a template of those limits.

Create a user

Users page → Add user; fill in the limits, tick the lines and save, and the subscription link is ready.

  • Username (subscription id): on the main panel the username is the subscription id by default, so no spaces or / ? # &. If "use the username in subscription links" is turned off in the settings, it is just a name and the link gets a random token.
  • Username: just a name; the subscription link gets a random token automatically.
  • With plans, choose the Plan and click Fill from plan to fill in every limit at once. Otherwise fill in Quota GB (0 = unlimited), Expiry (empty = never), Concurrent devices (0 = unlimited), Upload limit Mbps (0 = unlimited) and Download limit Mbps (0 = unlimited).
  • For monthly plans whose traffic resets, tick Periodic traffic reset and set the Reset period (days).
  • Tick the Lines. A line on several servers has several entries, and you can give just the entry on one server (switch between server groups; ticks are kept).
  • External nodes: ticked external nodes are added after your own nodes in the user's subscription.
  • Remark: an order number, contact details and so on.
Gift cards and trialsSet Expire N days after first connection (0 = off): the clock starts only when the user first uses traffic, and the expiry date is ignored.

How quota, expiry and devices are counted

Users who run over or expire are disabled and kicked automatically; renewing or resetting traffic brings them back.

  • Traffic: upload + download together; quotas can be decimals (0.1 is about 100 MB). Traffic through a server with a traffic ratio counts with that multiplier.
  • Expiry: the user is disabled when it passes. "Expire N days after first connection" overrides the expiry date.
  • Periodic reset: every N days used traffic goes back to zero, and users disabled for going over are re-enabled.
  • Devices: counted by source IPs online at the same time, across all servers. Several devices behind one Wi-Fi (one public IPv4, or one IPv6 /64) count as one; IPv4 and IPv6 are counted against the limit separately, so one device using both is not counted twice.
  • When the limit is reached only new devices are refused; connected ones are not affected. A slot frees up about a minute after another device goes offline.
  • Refused connections are shown in red as Refused: device limit in Recent inbound connections on the dashboard.
  • Speed limits: all of the user's connections share the bandwidth, and changes apply immediately.

Subscription links, QR codes and sharing

Click a user's name (or Details) to open the details; the subscription links and QR code are at the top.

  • Under Subscription, click Copy and send the link; phones can scan the QR code. The More menu in the list can also copy the Clash subscription, Link subscription or sing-box subscription.
  • Opened in a browser, the link shows the user's landing page: usage, expiry, one-tap import for each app and a QR code (see Subscriptions and landing page).
  • Shared: users can create a temporary link for a friend on their landing page; traffic and devices count against them. The details show that link, and Revoke cancels it at once.
  • Link leaked? More → Reset subscription link. The link gets a new random token, all protocol credentials are regenerated, the old link stops working and online devices are disconnected; send the new link to the user.
  • The details also show Online devices (IP) (and which line each IP uses), a traffic chart and the user's lines.

Renew, extend and change plans

In the More menu (or the user's details), Renew… and Change plan… handle renewals, upgrades and downgrades.

  • Renew…: Choose a plan (the user's current plan by default), then the mode: Renew (reset traffic, extend), Extend (keep traffic) or Only assign to this plan (keep quota and expiry). Periods renews several periods at once (1–120): enter 3 or 12 to sell a monthly plan quarterly or yearly. For a single user the new expiry and quota are previewed below as you type.
  • Extend 30 days: one click adds 30 days for users who have an expiry date.
  • Change plan…: choose the New plan and one of three ways under How:
    • Replace now: the new plan starts now for N periods; time and traffic left on the old subscription are dropped.
    • Stack: keeps the time left (and one-off traffic) and adds N periods; for plans with periodic resets traffic is a per-period allowance and does not stack.
    • Prorate: converts the value left on the old subscription into time on the new plan, using both plans' Reference price (optional); both plans need a price, and periods can be 0.
  • This period's usage: Auto (reset for replace and prorate, kept for stack), Keep (carry on) or Reset (new period).
  • The dialog previews Before and After live and marks it as an upgrade or a downgrade. Effects that hurt the user, such as an earlier expiry or going over quota at once, are shown in red, and you must tick I have read the effects marked in red, proceed anyway before Change plan works.
  • Every time the dialog opens it gets its own duplicate-protection id, so a double click or a network retry only runs once.
  • Plan history in the details lists recent renewals and plan changes.
Connecting a shopRenewals and plan changes are also available through the external API, with a preview before you commit (see External API).

Plans

A plan is a template of limits that new accounts, renewals and batch actions can apply directly.

  1. Plans page → Add plan: a Name (such as 100G/month), Description, Quota (GB), Duration (days), devices and speed limits.
  2. Tick Periodic traffic reset for monthly resets, and Start the clock at first connection for gift cards.
  3. Lines: applying the plan replaces the user's lines with these; empty = keep the user's lines.
  4. Rate-limit rules: ticked rules apply to every user of the plan, current and future.
  5. Reference price (optional): only used by "prorate" when changing plans and never shown to users; give two plans the same price to swap them at equal value.
  • The Plans page shows how many users each plan has.
  • Editing a plan does not change users who already applied it; renew or change their plan to move them to the new limits.
  • Resellers only see and use the plans they created themselves.

Batch actions

Tick several users and a batch bar appears at the top (the header checkbox ticks the current page only).

  • Enable, Disable, Extend, Apply plan, Reset traffic, Delete.
  • Bulk create: creates Count users at once from a Username prefix; for Naming choose prefix + 8 random chars or prefix + sequence (001…, random subscription URL). All the subscription links can be copied afterwards.
  • Export CSV: exports the user list.

Why a user is disabled, and kicking

The status column says why a user is disabled, which tells you how they come back.

  • over quota, expired: renewing, resetting traffic or extending the expiry re-enables them automatically.
  • manual: disabled by hand, and only enabling them by hand brings them back.
  • Limited: temporarily slowed down by a rule (see Rules).
  • Kick: closes the user's connections on every server (hysteria2, TUIC and AnyTLS sessions are closed entirely). If the user is still enabled the app reconnects right away, so disable them first to cut them off.
  • Filter the list with All, Enabled, Disabled, Expired or Over quota.

Import users from an old panel

Use this when your lines are already set up in m-ui and you only want to bring the old users over.

  • On the Users page click Import from old panel, upload the old panel's .db file and click Import.
  • Users with the same name only get their usage, quota, expiry and status updated; the rest are created with their old credentials (clients need no changes). You can tick Give newly created users every existing line.
  • To move lines, upstreams and settings too, see Moving from an old panel.

Rules (temporary speed limits)

Rules slow users down for a while: for example everyone at 30 Mbps in the evening peak, or 20 minutes of limits for anyone who used 1 GB within 10 minutes.

Two kinds of rules

  • Schedule: limits during a time window on chosen days of the week and lifts them outside it. Times use the panel time zone, and an end before the start means the window crosses midnight; no Weekdays ticked means every day.
  • Burst: when upload + download within the last Window (minutes) reaches Trigger (GB, up + down), the user is limited for Limit for (minutes); it lifts by itself and triggers again if reached again.

Create a rule

  1. Rules page → Add rule: give it a name, choose the Type and fill in the condition.
  2. Set Upload Mbps / Download Mbps; 0 leaves that direction unchanged.
  3. Tighten only: when on (the default) the result is never faster than the user's own limit; turn it off to apply the rule's values directly, for example to loosen limits at certain hours.
  4. Targets can be combined: all users (including future ones), users of a plan, all users of a reseller, or users ticked one by one.
  5. Save.
Limits by planYou can also tick Rate-limit rules while editing a plan so every user of that plan follows them.

Which limits are active

  • When several rules hit the same user, the strictest wins.
  • In the Active column, view shows who is limited right now and for how long; the user list also marks them Limited.
  • Changes apply to live connections immediately; the master evaluates rules every 10 seconds and syncs them to nodes. Disabling a rule lifts its limits at once.
  • Rule limits are not shown on users' landing pages. To hear about burst limits: Settings → Notifications → Notify when a burst limit triggers.

Reseller panel

Resellers sell accounts for you: you give them lines and quotas, they create users in their own reseller panel, and they only ever see their own users and the plans they made.

The reseller panel only covers the users under your account: the site owner gives you lines and quotas, and you create accounts, renew them and watch usage here.

Create a reseller

  1. Resellers page → Add reseller: the Name is the reseller's login name.
  2. Tick the Allowed lines: resellers can only give these lines to their users, and you can allow just the entry on one server.
  3. Set the limits: Traffic quota GB, Max users, Device pool, Bandwidth pool · up Mbps / Bandwidth pool · down Mbps, Expires (empty = never); 0 = unlimited.
  4. Send them the reseller panel address shown at the top of the page (default port 2054, path /dl/).
  • New resellers have no password: within 24 hours they sign in with their name and an empty password, then set one. If that window passed or they forgot the password: More → Reset password (this also clears their 2FA and API token and opens a new 24-hour window).
  • Unticking a line removes it from all of that reseller's users at once.
  • Reset traffic sets the used traffic of all their users back to zero.
  • Resellers' users do not appear on the main panel's Users page; open the reseller's Details to see them.
  • The reseller panel's port, path and certificate are under Settings → Reseller panel; untick Enable the reseller panel if you do not need it, and remember to open 2054/tcp in the firewall.

How reseller limits work

  • Traffic quota: counts all usage of all their users; resetting traffic, renewing or deleting users on the reseller panel does not reduce it. Only "reset traffic" on the main panel sets it back to zero.
  • Device pool: the most devices all their users may have online at once (across all servers). When it is full only new devices are refused; connected ones are not affected.
  • Bandwidth pool: the combined speed of all their users, one pool per server.
  • Any single user can be given any value, but the totals are capped by these pools.
  • If the reseller expires, is disabled or runs over the traffic quota, all their users are disabled at once and their subscriptions stop working.

First sign-in and password

  1. Open the reseller panel address you were given (default http(s)://SERVER:2054/dl/).
  2. Enter your reseller name as the username; the first time, leave the password empty and click Sign in.
  3. When asked, Set a password (at least 8 characters), and sign in with it from then on.
Common pitfallA new reseller account can only be claimed within 24 hours. If it expired or you forgot the password, ask the site owner to reset it on the main panel, which opens a new 24 hours. After signing in, turn on two-factor authentication on the Account page.

What the reseller panel can do

  • Dashboard: traffic used against the quota, number of users, online users and devices.
  • Users: add, edit, renew, extend, reset traffic, kick, reset subscription links, batch actions, usage charts and online devices. New users only need a name; their subscription link is a random token.
  • Plans: only the plans you created yourself are visible and usable.
  • Account: quota, password, two-factor authentication, your own subscription page texts and the external API.
  • You can only assign the lines the site owner allowed (possibly just on some servers).

Account page

The reseller panel's Account page holds your sign-in security, your quota, and the subscription page your users see.

  • My quota: traffic used, the device pool (online / limit, and the total handed out to users), bandwidth, expiry and number of users. When the device pool is full it also says how many new devices were refused recently.
  • Password: change your password.
  • Two-factor authentication (2FA): see Account and two-factor authentication.
  • Subscription page: the texts your users see: Profile title (the subscription name shown in apps), Page title, Footer contact, Purchase / renew link and Notice (multi-line); empty fields use the main panel's. You can also turn off the page or temporary sharing for your users.
  • Landing page logo: upload your own logo; without one, the main panel's is used.
  • External API: for your own shop or bot (see External API).

Subscriptions and landing page

Clients import the subscription link; the same link opened in a browser is the user's own landing page.

Subscription links and formats

  • They look like http(s)://DOMAIN-OR-IP:2056/sub/USERNAME (or a random token).
  • One link is enough: the format follows the client that fetches it. Clash-type apps (Clash Verge, mihomo, Stash) get a Clash config, sing-box apps (SFA, SFI and so on) get a sing-box config, and NekoBox, v2rayN, Shadowrocket and others get plain links.
  • To force a format, append ?format=clash (Clash), ?format=json (sing-box) or ?format=mihomo (Clash for the new core).
  • Each line appears once per server, with the server name as a suffix; servers whose traffic ratio is not 1 get a tag such as x2.
  • Node addresses are server IPs by default (the domain is only the SNI), so a poisoned DNS on the client cannot break them.
  • Disabled, expired or used-up users get a 404 when their client fetches the subscription, and the lines stop letting them in.

How users import it

  • Easiest: send the link and have the user open it in a phone or computer browser, then tap one-tap import for their app or scan the QR code.
  • The download arrow at the top right of the one-tap import button opens a download page with apps for each system (iOS, Android, Windows, macOS, Linux); it holds no user data and can be forwarded as is.
  • Users can also copy the link and paste it into their app's "add subscription".
  • The name shown in apps comes from Profile title. Shadowrocket and Clash Verge fix the name when the subscription is added, so after changing the title users must remove and re-add it, or use one-tap import on the landing page (which carries the title).

Subscription settings

Under Settings → Subscription and Subscription formats and templates.

  • Profile title, Update interval (hours).
  • Use the username as the subscription URL: on by default; when off, new users get random tokens and existing users keep their links.
  • Allow insecure certificate in subscriptions: automatic by default (on with a self-signed certificate).
  • Node address in subscriptions: IP (recommended) or domain.
  • Base64-encode link subscription, Show traffic notice node on top, External subscription refresh interval (minutes).
  • Pick the format by client: on by default; when off, links without ?format= always get plain links.
  • Custom templates: Clash template (YAML, empty = built-in) / sing-box template (JSON, empty = built-in). Start with Fill in the built-in Clash template and edit it; nodes and groups are filled in by the panel, and mistakes are reported when you save.
Common pitfallChanging the subscription Path or port breaks every existing subscription link; send users their new links.

Landing page

What users see when they open their subscription link in a browser: usage, expiry, one-tap import, QR codes, plus your notice and contact details.

  • Edit it under Settings → Subscription page; resellers edit theirs under Account → Subscription page (empty fields follow the main panel).
  • Edit it under Account → Subscription page; empty fields use the main panel's.
  • Show a page when the subscription URL is opened in a browser: when off, browsers just get the subscription content.
  • Page title, Footer contact, Notice (multi-line).
  • Purchase / renew link: adds a purchase / renew button to the landing page (the main button when the user has expired, run out or been disabled).
  • Show “Powered by m-ui” at the bottom of landing pages: resellers' landing pages never show it.
  • Landing page logo: click Upload / replace; it applies at once, no save needed. PNG, JPEG, GIF, WebP and SVG are accepted; the browser scales the image to fit 480×160 and converts it to PNG (64 KB at most). It is shown 28 pixels high on the landing page and used as the browser tab icon. Restore default brings back the built-in logo. Resellers without a logo use the main panel's, and nodes follow the master.
  • Users who ran out, expired or were disabled can still open their landing page, which shows the reason and whom to contact; their clients get a 404. Links that match no user show an "invalid subscription link" page in browsers.

Links in the notice and contact details

Notice (multi-line) and Footer contact can contain clickable links; only the text is shown on the page.

Temporary sharing

Users can create a temporary link on their landing page for someone else, and take it back any time.

  • One per user; the other person gets the same nodes with a separate set of credentials. Traffic, devices, speed and expiry all count against the owner.
  • Cancelling or regenerating it stops the old shared link at once and disconnects whoever was using it.
  • Opened in a browser, a shared link shows a reduced landing page without the owner's usage or expiry.
  • Let users create a temporary share link (on by default) turns the feature off for everyone: on the main panel under Settings → Subscription page, for resellers under Account → Subscription page (if the main panel turns it off, resellers cannot turn it on).
  • The user's details show their shared link; Revoke cancels it at once.

Backup and migration

One zip file is the whole panel: the database (lines, users, traffic, settings) plus certificates. Keep it safe and you can move or reinstall without losing anything.

Back up

  • Backup page → Backup now: Download it, or Save on server (listed under Backups on server).
  • Scheduled backup: Hour of day (-1 = off) (server local time) and Copies to keep; tick Also push to Telegram once Telegram notifications are set up.
  • Command line: m-ui backup -db /etc/m-ui/m-ui.db -out backup.zip, or option 9 in the m-ui menu.
Common pitfallBackups contain every user's credentials and the certificates' private keys; never put them anywhere public.

Restore

  1. Backup page → Restore: choose the backup file (zip or .db) and click Restore.
  2. After you confirm, m-ui restarts by itself and replaces the database and certificates; the previous database is kept as a .bak-* file.
  • A new server can install and restore in one step (the command is in the migration wizard below).
  • With the service stopped you can also restore from the command line: m-ui restore -db /etc/m-ui/m-ui.db -from backup.zip.

Moving to another server

The Migration wizard on the Backup page moves the whole panel in four steps; ports, credentials and subscription links stay the same, so users notice nothing.

  1. Install m-ui on the new server and restore the backup (the wizard has the ready-made command; certificates are restored too).
  2. Open the panel with the new server's IP (same port and path as before) and check that the lines are running; nodes are reconnected automatically.
  3. Point your domain to the new IP at your DNS provider, and use Check DNS in the wizard to see whether the major resolvers have picked it up.
  4. When users are fine on the new server, stop the old one: systemctl stop m-ui.
Replacing only a node is simplerInstall the new node, then on the master's Servers page update that row with the new API URL and token; the master pushes everything again.

Moving from an old panel

  • Everything (lines, upstreams, users, settings): add a parameter when installing, bash install.sh --import /path/to/old-panel.db. Ports, user credentials, the panel path and subscription links are kept, so clients need no changes.
  • Users only: Users page → Import from old panel (see Import users from an old panel).

Notifications (Telegram)

Get alerts on Telegram (or a webhook): users expiring, upstreams failing, certificate renewals failing, servers getting blocked… and manage users from your phone with the bot.

Set up Telegram notifications

  1. In Telegram, create a bot with @BotFather and copy its token (like 123456:ABC-DEF…).
  2. Message @userinfobot to get your chat ID (group and channel IDs are negative). Then send your own bot a message, otherwise it cannot write to you.
  3. Settings → Notifications: tick Enable Telegram notifications, fill in Bot token and Chat ID, click Save.
  4. Click Send test message; if it arrives on your phone, you are done.
Common pitfallIf the server cannot reach Telegram (in mainland China, for example), set a Proxy (optional); with WARP installed use socks5://127.0.0.1:40000.

What gets notified

Tick each event in the Notifications group; Telegram and the webhook share these switches.

  • Panel login / repeated failures
  • User auto-disabled (expired / quota), User expiring soon (how early: Days before expiry), User quota warning (at Warn at usage percent)
  • Notify when a burst limit triggers
  • Upstream down / recovered, Data plane stopped / recovered
  • Mainland reach problem / recovered
  • Certificate issued / renewal / expiry (node certificates are reported by the master too)
  • Daily report, sent at Daily report hour (0-23, panel time zone)
  • Master failover: candidates report a lost master, a finished takeover and a finished move-back here too (see Master failover).

Webhook

To feed alerts into your own system (a chat relay, a ticket system…), use a webhook.

  • Webhook URL: ticked events are also POSTed here as JSON with event, text and time. Empty = not sent.

Ops, logs and updates

Tune the server, read logs, troubleshoot connections and update, all without a terminal.

System tuning

System tuning on the Ops page: swap, the open-file limit, time sync, kernel parameters and BBR; the defaults suit most VPSes.

  • Tune everything applies them all, or adjust one item and click Run; progress appears live in Task output.
  • The same page can cap the system log (journald) size and retention. It holds the logs of every service on the machine; limiting it does not affect the panel.
  • WARP is on this page too (see WARP). Ops tasks only work on Linux with m-ui running as root.

Logs

The Logs page has three kinds: Subscription access, Core log and Audit.

  • Subscription access: who fetched a subscription, from which IP and with which app.
  • Core log: the data plane's and panel's runtime log, kept in memory only (up to 10,000 lines, cleared on restart). Logging can be switched off to save resources.
  • Data-plane level: warn by default, warnings and errors only. Switch to info or debug while troubleshooting (it applies at once) and back to warn afterwards; info writes tens of thousands of lines an hour and slows the disk down.
  • Audit: who did what and when (panel, external API and Telegram bot actions).
  • Subscription access and audit logs can Auto-clean (keep 1 day, 1 week, 1 month or forever); every kind can be emptied with Clear.

Recent inbound connections

Recent inbound connections at the bottom of the dashboard helps when a user says they cannot connect: did their IP reach the server, and on which line?

  • It lists connections that passed the protocol handshake and authentication, with user, line, server, count and last time.
  • Connections refused by a device limit or a reseller's device pool are listed in red too: Refused: device limit, Refused: reseller device pool full.
  • Connections that failed the handshake or authentication (wrong certificate, password or SNI) are listed as well, with the reason.
  • An IP missing from the list usually means the packets never reached the server (security group, firewall, client network). To check whether they arrive, set Data-plane level to info for a while and look for inbound connection from, or capture packets on the server.

Updating

When a new version is out, an arrow appears next to the version number at the bottom left; click it to update in one step.

  • Arrow → Update now: the download is verified, the program replaced and restarted, and the panel reloads after a dozen seconds. Users, lines, subscription links and certificates stay as they are; connections on this machine drop for a moment.
  • If the new version fails to start, the old one is put back automatically and a bar at the top explains it; Got it dismisses it.
  • Nodes are full installations and update from their own panels; keep master and nodes on the same version.
  • You can also run m-ui over SSH and choose option 10, or run the one-line installer again. IPv6-only servers cannot reach GitHub until WARP is installed.

Command line and SSH menu

If the panel will not open or you forgot the password, run m-ui on the server for a numbered menu.

  • Menu: 1 show panel address / account, 2 restart, 3 stop, 4 start, 5 reset the admin password, 6 change panel port / path / subscription port, 7 reset all settings, 8 recent logs, 9 back up now, 10 update to the latest version, 11 generate a self-signed certificate, 12 switch between master and node, 13 turn off two-factor authentication, 14 uninstall.
  • m-ui info: prints the panel address, path and account status.
  • m-ui passwd: resets the admin password (and turns off two-factor authentication).
  • m-ui set -db /etc/m-ui/m-ui.db key=value: changes a setting directly, such as webPort=3053.
  • m-ui render: prints and validates the current sing-box configuration.
  • Data lives in /etc/m-ui/: m-ui.db (database), cert/ (certificates), backups/ (scheduled backups).

Settings at a glance

The Settings page saves group by group, each with its own Save. Groups marked restart to apply need Restart m-ui (top of the page) after changes.

Role and panel

  • Role: Run as node (secondary server) (see Attach a node).
  • Panel: Domain (the domain used by subscriptions and nodes, also the TLS SNI), Time zone (all times in the panel use it), Listen address, Port, Path, Certificate / Private key (normally filled in from the Certificate page), Supporters list and online panel count.
  • A new panel path applies as soon as you save and the browser follows it; port, listen address and certificate changes need a restart.
  • With port 443 (HTTPS) or 80 (HTTP), addresses need no port number; the panel and subscriptions cannot share a port.

Subscriptions, subscription page, reseller panel

  • Subscription, Subscription formats and templates: see Subscription settings.
  • Subscription page: landing page texts, the purchase link and the sharing switch; see Landing page.
  • Reseller panel: Enable the reseller panel, listen address, port (default 2054), path (default /dl/) and certificate (empty = same as the panel).

Notifications, health checks, data plane

  • Notifications: see Notifications (Telegram).
  • Upstream health checks: Interval (minutes) (0 = off), Consecutive failures before alert.
  • Mainland reachability: Automatic checks, Interval (minutes), Globalping token (optional).
  • Data plane: Data-plane certificate, Upstream test URL, Stats bucket (seconds), Keep traffic history (days), Let users reach private / local addresses (off by default), Block BitTorrent. Changing the last two restarts the data plane once and syncs to nodes.
  • About: version number and what the panel and subscription addresses look like.

External API

For shops, billing systems and bots: with one token they can create users, renew, change plans, enable or disable users and fetch subscription links, without signing in to the panel.

Turning it on

  1. Admin page → External API: switch on Enable / disable the external API, then copy the Base URL and the Token.
  2. Account page → External API: switch on Enable external API, then copy the Base URL and the Token.
  3. Send the token with every request: the header Authorization: Bearer TOKEN (or X-API-Key: TOKEN), with JSON request bodies.
  4. The endpoint list further down that page explains every call with a curl example you can copy.
Common pitfalls
  • The token carries all of your panel permissions: keep it in server-side code only, never in a web page or an app. If it leaks, click Regenerate and the old token stops working at once.
  • Call the API on the master only; write calls on a node are refused.
  • A reseller token only reaches your own users, your own plans and the lines you were allowed; it stops working as soon as you are disabled, expire or have your password reset.

Preview, no duplicates, confirm downgrades

Renewals and plan changes touch users' money and time, so the API has three safety nets.

  • Preview: "dryRun": true only calculates and returns before / after, which a shop can use for quotes.
  • No duplicates (idempotency): send a requestId (or the Idempotency-Key header, such as your order number) and retries with the same id run only once, so time is never added twice.
  • Downgrade confirmation: if a plan change would put the user over quota at once or bring the expiry forward, the API answers 409 with the full preview; call again with "force": true to go ahead.
  • Calls marked "idempotent" and "preview" in the panel's endpoint list support these.

Security

A changed default password, two-factor authentication and a hidden panel address stop most trouble.

Account and two-factor authentication

  • Change the password or username: Login account on the Admin page.
  • Change the password: Password on the Account page.
  • Two-factor authentication (2FA): click Generate secret, scan the QR code with an authenticator app (Google Authenticator, Microsoft Authenticator, Authy, 1Password…), enter the 6-digit code it shows and click Verify & enable. From then on signing in needs the password plus a code.
  • Lost your phone? SSH in and run m-ui: option 13 turns two-factor authentication off; resetting the password with option 5 turns it off too.
  • Lost your phone or password? Ask the site owner to reset your password on the main panel (two-factor authentication is cleared with it).

Panel address and ports

  • Change the default port and path: Settings → Panel → Port / Path. IP:port/ alone always returns 404, so a port scan does not reveal the panel.
  • Serve the panel over HTTPS: when adding a certificate, tick Use for panel HTTPS (applies after a restart).
  • Open only the ports you need in the firewall, and allow nodes' panel ports only from the master's IP.
  • Login protection: 10 wrong attempts from one source within 10 minutes block it for 5 minutes, and 5 wrong attempts in a row can send a Telegram alert (Panel login / repeated failures).

Data-plane safety switches

  • Let users reach private / local addresses: off by default, so users cannot reach the panel, the WARP port or your internal network through the proxy. Turn it on only if users really need internal services.
  • Block BitTorrent: refuses BitTorrent through the proxy so your VPS does not attract copyright complaints.
  • Give nodes HTTPS API URLs; otherwise tokens and user credentials are synced in plain text.
  • Backup zips contain user credentials and private keys, and the external API token equals admin rights: keep all of them safe.

FAQ and troubleshooting

Start from the symptom; if it is not here, search for a keyword at the top.

Cannot connect

The subscription refreshes, but nodes do not connect?
Have the user refresh the subscription once, then check in this order: is the line's port open in the security group / firewall (Hysteria2 and TUIC need UDP); is the user disabled (see the status column); is the device limit full. Recent inbound connections on the dashboard shows whether their IP reached the server.
Device limit reached / some devices cannot connect?
The devices online at the same time (by source IP, across all servers) hit the limit, so new devices are refused. Wait about a minute after another device goes offline, or raise the limit. A phone switching between Wi-Fi and mobile data changes IP and may count twice for a short while.
IPv6 nodes do not work?
Usually the cloud security group lacks ::/0 rules (add TCP and UDP separately) or ip6tables / ufw blocks it; also make sure the user's own network has IPv6. Outbound-only IPv6 such as WARP or NAT cannot take incoming connections. The IPv6 inbound check on the Servers page tells you directly whether it is reachable.
Everyone in one region suddenly cannot connect?
On the Servers page click Check mainland reach: IP blocked means change the IP, Port blocked means change the port.

Panel and servers

Opening IP:2053/ shows 404?
On purpose: the root does not redirect, so the panel path is not given away to scanners. Open the full address, such as http://IP:2053/app/. Forgot the path? SSH in, run m-ui and choose option 1.
Forgot the password / lost the 2FA phone?
SSH in and run m-ui: option 5 resets the admin password (and turns off 2FA), option 13 only turns off 2FA.
Port, listen address or certificate changes do nothing?
They need a restart: Restart m-ui at the top of the Settings page, or menu option 2. A new path applies on save.
A node shows offline?
Read the reason on the Servers page and see offline nodes. Nodes with self-signed certificates need Skip certificate verification; after re-issuing a node's certificate click Reset fingerprint.
Certificate renewal fails?
Check the reason in the Auto-renew column of the certificate store: HTTP validation needs port 80 free; manual-DNS certificates cannot renew automatically; an AAAA record pointing elsewhere also breaks validation. See Automatic renewal.
WARP will not enable?
Read the task output on the Ops page; most often port 40000 is taken, so set another SOCKS5 port and enable again.
Subscriptions return 429?
One IP fetched a subscription more than 120 times in a minute and was rate-limited, usually an app refreshing too often. If you really need more, run m-ui set -db /etc/m-ui/m-ui.db subRateLimit=COUNT on the server (0 = unlimited).

Subscriptions and users

The subscription name in the app is wrong?
Set Profile title under Settings → Subscription (resellers set theirs on their Account page).Set Profile title under Account → Subscription page. Shadowrocket and Clash Verge fix the name when the subscription is added, so users must remove and re-add it, or use one-tap import on the landing page.
What do users see after running out or expiring?
Their landing page still opens in a browser, with the reason, contact details and a renew button (if a purchase link is set) at the top; their apps get a 404. Renewing or resetting traffic brings them back at once.
A subscription link leaked?
The user's More → Reset subscription link: the old link and credentials stop working at once; send the new link.
A reseller cannot sign in?
New resellers sign in the first time with an empty password. If the 24-hour window passed or the password is forgotten, the site owner uses Resellers → More → Reset password on the main panel.
