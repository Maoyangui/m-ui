# 流量奖励的登记服务

面板这一侧(数真实流量、活动页、上报)在仓库的 `reward/`、`runner/reward.go`、`web/reward_api.go`;这个目录是它对面的那一半:
一个 Cloudflare Worker + 一个 D1 库。它收面板的上报、给地址入账积分、自动识别作弊、算奖池,并把这一切出成一份公开账本。

| 文件 | 是什么 |
| --- | --- |
| `worker.mjs` | 登记服务本体 |
| `schema.sql` | 它自己那个库的表 |
| `wrangler.toml` | 部署配置 |
| `ledger-workflow.yml` | 把账本定时提交到 `rewards` 分支的工作流。**放在这里不会运行**,上线时复制到 `.github/workflows/reward-ledger.yml` |
| `check-ledger.mjs` | 提交前核对账本(写法、自洽、只增不减);任何人也可以拿它核对分支上的那份 |
| `payout.mjs` | 发放那天每个地址该发多少,拿公开账本就能自己算 |
| `dev-server.mjs`、`devkit.mjs` | 本地试跑:假的订单库、模拟的链,什么真实的东西都不连 |
| `*.test.mjs` | 测试(`node --test deploy/reward/*.test.mjs`,CI 里也跑) |

## 规则

**积分。** 面板只数线路上的真实流量(上行 + 下行的原始字节,不乘倍率)。登记了 Solana 地址的面板每半小时把累计值(取整到 GB)报上来,
每满 1 TB 是 1 积分。一个地址下可以有几台面板,合在一起算。

**入账。** 每个地址每天最多入账 1 积分,而且当天要有它名下的面板在上报;挣到的比入账的多,多出来的顺延到后面的日子,不作废。
一台面板一天最多算进 25 TB(约等于 2.4 Gbps 跑满一整天),头一次登记能带进来的历史累计也按这个上限算。

**换地址。** 7 天的冷却期。换了之后,这台面板以前的流量留给原地址,之后新增的才算到新地址。

**自动识别作弊。** 没有人工的环节,只有三条固定的规则。判的是**面板**,不是地址:

| 代号 | 什么情况 | 怎么处理 |
| --- | --- | --- |
| `same_src` | 一处来源(一个公网 IPv4 地址;只有 IPv6 的机器按 /48)上同时有几个地址在登记 | 只认先在这处来源上报的那个地址,后到的面板剔除;刚登记(不满一天)就被判的,带进来的历史累计一并作废 |
| `twins` | 两台面板连续 7 天每天涨的流量都一样(同一份流量登记了两次) | 只认先登记的那台,另一台剔除,它报过的全部作废 |
| `robot` | 连续 14 天每天涨的流量一模一样(真流量每天都不一样) | 剔除,它报过的全部作废 |

- **剔除** = 这台面板报的流量不再计入。条件消失后连续 14 天没有再命中,自动恢复;被剔除期间报的流量不补记。
- **作废** = 这台面板已经算进去的流量拿掉;地址已入账的积分要是因此比挣到的多,多出来的那几分一并作废。
- 一个地址名下的面板**全都**被剔除着,榜上才会把这个地址标出来并写明原因;这期间它不参加分配(积分留着,恢复后照旧)。
- 每一次剔除、恢复、作废都记在账本的 `events` 里。

为什么判面板不判地址:面板上填谁的地址都行,不需要证明那是自己的。按地址判的话,任何人都可以把别人的地址绑到一台作弊的面板上,
害那个地址被剔除。按面板判,被剔除的只是那台作弊的面板;被冒用的人自己的面板照常算,最多是别人「送」的那部分被作废。

**做不到的事。** 面板是开源自建的,累计值由面板自己报,改过的程序想报多少报多少;签名只能证明「是同一台面板报的」。
所以这套规则防的不是数字造假本身,而是让造假不划算。能保证的只有一条,但它是硬的:

> 每天入账的积分总数 ≤ 当天有面板在上报的「来源」的个数。

想多拿一分,就得多一处来源,也就是多租一台有独立公网地址的机器。共用出口地址的机器(NAT 机)上,只有最先登记的那个地址算,这是这条规则的代价。

## 奖池

奖池 = 订阅站里已发放、现在还在的订单金额 × 40% + 全部留名捐赠(全额)。入账只加不删;合计只在订单取消(退款)时才会变少,那一笔留在账本上标成作废。

- **订单**:只读订阅站的订单库,两条链都算。计入的是「已发放」(`orders.status = 'fulfilled'`)的订单:
  - 监听到账的:`payments.status = 'credited'`、挂着的那张订单还在且已发放 → 按到账金额记,带链上交易号。
  - 人工确认发放的(订单已发放、却没有监听到账的付款 —— 付款金额对不上,管理员核对后补发):订单从下单到发放这段时间里,
    打到它收款地址上、被订阅站标成「金额对不上」的付款恰好只有一笔 → 按那一笔实收的金额记、带它的交易号;找不出唯一的一笔 →
    按订单金额记、没有交易号。两种都标 `note: "manual"`。
  - 监听到账之后订单不再是已发放的(标了已退款,或者删掉了)→ 那一笔标 `void: true`:留在账本上,不进任何合计。
  平时每一轮只看最近变动的付款;作废和人工确认要对全表,每小时一遍(读的是订阅站的库,省着读)。
  订单号是订阅的使用凭证:只拿订单的状态、金额、收款地址、时间,订单的标识只出现在连接条件里、从不取出来(测试逐条核对查询)。
- **捐赠**:只认留名捐赠。先登记「留名 + 金额」,拿到一个带零头的确切金额(在填的数上加 0.001–0.099,第三位小数不为 0 —— 整分的数太像一笔普通转账),60 分钟内这个数转到奖池的 Solana 地址,
  就全额计入奖池并记上名字。认的是链上的到账时间(前后留 5 分钟余量),登记服务晚一点才看到也照样算。
  订单金额的第 6 位小数一定不是 0(订阅站生成金额时的规则),留名捐赠最多 3 位小数,所以两者永远不会相同;
  万一订阅站把同一笔交易认成了订单付款,按订单算,不重复记。
- **不计入的**:没登记就直接转进来的、过了期限才到的、金额对不上任何一笔登记的,一律不计入、也不列出。
  这个地址上还有订单付款和别的资金流动,只有对得上一笔登记的转入才能确定是给奖池的。TRON 上只有订单,没有捐赠。
- **取消**:`POST /v1/donate/<id>/cancel` 只是让面板上收起这一笔。钱要是真的在期限内按那个数转来了,照样计入、照样记名
  (钱不能因为点了一下取消就白转);那个金额在期限过完之前也不会发给别人。
- **怎么查账**:没有留名在等到账的时候,一次链都不查。有的时候,每两分钟拉一次奖池收款账户的新交易号,
  只有时间落在某一笔登记期限里的交易才去看金额(一次请求问一批)。收款账户(USDT 的关联代币账户)的地址是本地算出来的,不用问链。
  订阅站只在有待付订单的时候才扫链,所以到没到账由登记服务自己看。

登记服务对订单库**只读**。Cloudflare D1 的绑定没有「只读」这个选项(绑上就能写),所以这件事由登记服务自己保证,有三层:
- 代码里对订单库只有 `SELECT`,只碰 `payments`、`orders`(状态 / 金额 / 地址 / 时间)、`order_payment_options`、两张收款地址表、
  `solana_amount_reservations` 这六张表(测试读源码逐处核对);
- 拿到订单库的句柄时先套一层(`readOnly`):只有 `prepare`,只收单独一条 `SELECT`,没有 `run`、`batch`、`exec` ——
  以后哪段代码想写订单库,语句到不了库(测试里拿一份能写的句柄跑整套流程,订单库一个字节不变);
- 不读订单表。付款记录里只取链上交易号、收款地址、金额、时间和付款方地址;订单号、订单的哈希一概不取,
  登记服务的库和公开账本里都没有(测试核对)。

## 公开账本

`GET /v1/export` 是账本本身;`ledger-workflow.yml` 每一刻钟取一次,过一遍 `check-ledger.mjs` 再提交到仓库的 `rewards` 分支。
没登记地址的面板只读分支上的那份文件;分支的提交历史就是奖池和积分每一次变动的记录。

账本里有:奖池合计(订单的 40% 和留名捐赠各是多少)、收款地址、逐笔入账(金额、链、付款地址、链上交易号、留名)、积分榜(地址、积分、面板数、被剔除的原因)、剔除 / 恢复 / 作废的记录。
账本里没有订阅站的订单号:登记服务不读订单表,只读付款记录里的金额、链、时间和链上交易号。
每一笔入账都能拿交易号去区块浏览器上核对。

## 隐私

- 面板上报的只有:面板的公钥(随机生成的一把,和面板的别的东西无关)、填的地址、累计流量(GB)、时间、签名。没登记地址的面板什么都不上报。
- 登记服务会看到上报来自哪个 IP(任何服务都一样)。它只存一个加盐的哈希,用来判断「一处来源只认一个地址」;不存 IP 本身,也不公开。
- 账本里没有面板的公钥全文(记录里只有头 8 位)、没有 IP、没有任何用户数据。

## 部署

需要:订阅站所在的那个 Cloudflare 账号、`wrangler`、`godusevpn.org` 的 DNS 在这个账号下。

```bash
cd deploy/reward
wrangler d1 create m-ui-reward                                        # 记下它给的 database_id
# 另存一份配置(别提交):把上面的 database_id 填进 DB,订阅站订单库的 database_id 填进 COMMERCE(在订阅站自己的 wrangler 配置里)
wrangler d1 execute m-ui-reward --remote --file schema.sql -c 那份配置
openssl rand -hex 32 | wrangler secret put SALT -c 那份配置
wrangler deploy -c 那份配置
curl https://reward.godusevpn.org/v1/health                           # 定时任务跑过第一轮之后,这里能看到 at / errs
                                                                      # (新建的定时触发要等一阵才开始执行,Cloudflare 说最长一刻钟)
curl -o ledger.json https://reward.godusevpn.org/v1/export && node check-ledger.mjs ledger.json
```

核对订单笔数:账本里的 `pool.orderCount` 应当等于订阅站后台里已经到账的订单数。对得上之后,把 `ledger-workflow.yml` 复制到
`.github/workflows/reward-ledger.yml` 提交,账本就开始进 `rewards` 分支。

**套餐。** 免费套餐一次调用最多 50 个子请求,定时任务按预算干活(干不完的留给下一轮),测试里逐轮核对没有超。面板上了千台之后建议换付费套餐。

**Solana 节点。** 内置了三个公共节点,轮着用:哪个限速了、或者把这一次请求挡了(403),就让它歇一会儿(1 分钟起,连着不行就翻倍,
最长 30 分钟)换下一个;哪个明说不给某种查询(要令牌、要付费)才一天内不拿它问那种查询;不认批量请求的改成一笔一笔问。全都不行的
那一轮看不了链上的转入,留名和钱都不丢,节点好了之后补上(积分入账、订单同步不受影响)。平时很省:没人捐的时候不查链,
有人在等到账时一轮两三次请求。

公共节点里只有官方那个(api.mainnet-beta.solana.com)留着全部历史,另外两个只留最近几小时到一天的记录(2026-11 量过:
9 小时、25 小时)。所以:

- 问节点「这个账户有哪些新交易」时不带「上次看到哪一笔」—— 只留近期记录的节点碰到一个它不记得的交易号会整个报错,一条都不给
  (2026-11-19 一笔留名捐赠到了账却认不出来,就是这个原因,加上官方节点那天把登记服务挡了一次、被旧代码停用了一整天)。数到哪为止由登记服务自己数。
- 这种节点答「没有更多了」「没有这笔交易」,只在近期(3 小时)之内当真;再久的,这一轮换别的节点再问,还是没凭据就不算查完:
  留名一直留着等(最长到 7 天后被清理),看到的交易照样对账。查不到的交易要过一天、问过 30 轮才划掉。
- 官方节点对云主机的出口地址时不时答 403。**建议在 `SOLANA_RPC` 里填一个自己的节点**(可以写几个、逗号隔开),它们排在
  公共节点前面:只靠公共节点,到账要等到有一个节点答得上来才认得出(钱不丢,但页面会一直停在「等待到账」)。

留名的答复(`POST /v1/donate`、`GET /v1/donate/<id>`)里带 `scanAt`(登记服务上一次把链上看全的时间)和 `now`(它答复时的钟)。
面板拿它们做两件事:`now - scanAt` 超过 6 分钟就在等待到账的页面上说明「查账卡住了,钱不会丢,查得到了自动补记」;
倒计时走完之后,`scanAt` 没过「期限 + 5 分钟」之前不说「没成立」,显示「正在核对」。

**付了款多久显示。** 定时任务两分钟才看一次链。面板开着等待到账的页面时每 4 秒问一次这一笔的状态;登记服务被问到一笔还没结论的留名,
就当场看一次链(`quickScan`,和定时任务是同一段代码):全站最多 5 秒一次,登记超过 10 分钟还没转的 15 秒一次;最多让问的人等 3.5 秒,
没看完先回话、后台接着看,下一次问就有结果。所以付款后一二十秒页面就能跳;没有人开着页面时仍然只有定时任务在看。
被限速的节点在歇着的时候,当场看链不去敲它(那样只会让它歇得更久),等它醒了、或者等定时任务两分钟一次的试探。问一个节点最多等 8 秒,
答不上来按出错算、换下一个。

**改门槛。** 都在 `worker.mjs` 开头的 `CFG` 里(每天上限、冷却期、各条规则的天数和容差、留名的期限)。改完跑一遍测试再部署。

**备份。** `wrangler d1 export m-ui-reward --remote --output backup.sql`。奖池那部分丢了可以从订单库和链上重建;积分和面板的记录只在这个库里,要定期备份。

## 本地试跑

```bash
node deploy/reward/dev-server.mjs 8787
M_UI_REWARD_API=http://127.0.0.1:8787/v1 M_UI_REWARD_LEDGER=http://127.0.0.1:8787/v1/export m-ui run -db ./dev.db
```

试跑的服务器多几个开发接口:`POST /dev/pay {"amount": 10.037}`(模拟一笔链上到账)、`POST /dev/order {"amount": 9.99}`(订阅站认了一笔订单)、
`POST /dev/tick`(马上跑一轮定时任务)、`GET /dev/state`(看库里的情况)。它的奖池地址是启动时随手生成的,没有人有私钥,千万别往里转钱。

## 发放

2027-09-03 按公开账本上的积分比例发放。每个地址的金额任何人都能自己算出来:

```bash
git show origin/rewards:ledger.json > ledger.json
node deploy/reward/payout.mjs ledger.json
```

算法只有一条:金额 = 奖池 × 这个地址的积分 ÷ 全部积分,向下取到 0.01 USDT;名下面板全被剔除着的地址不参加。实际的转账由项目方在链上完成,
每一笔的金额和交易号发放后公开。
