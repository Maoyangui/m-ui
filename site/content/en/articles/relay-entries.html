Relay entries: letting users connect through another machine

The exit server's route is fine; the leg from the user to it is not — a detour, packet loss, or an IP the user simply cannot reach. The usual answer is a machine in between that the user reaches well. In m-ui that is a relay entry. This guide covers how it works, and the one symptom that confuses people most.

Two ways "through another machine"

m-ui has two ways to pass traffic through one more server, and they are not the same thing:

  • A line as an upstream (proxy chaining): the middle server runs a line of its own, decrypts the user's traffic and connects to the exit as a client. Two separate connections; the middle server runs the protocol, needs a certificate and pays for a second round of encryption.
  • A relay entry: the middle server only moves bytes. There is still one encrypted connection between the user and the exit; the relay cannot see inside and does not need to understand the protocol. TCP and UDP both work, so Hysteria2 and TUIC do too.

Most of the time the second is what you want: cheaper, simpler, half the crypto. The path is "user → relay → exit (this line's server) → website".

Adding one

Edit the line, open Relay entries and click "+ Add a relay entry". Each entry reads as a sentence: users connect to which relay on which port → forwarded to which exit.

  • Another server of your cluster as the relay: the panel sets up the forwarding on it and picks a free port there. That server's firewall (the cloud security group) must allow the port — UDP for Hysteria2 / TUIC, TCP and UDP for Shadowsocks, TCP for everything else.
  • "A relay elsewhere (enter address)": one you run yourself with realm or iptables, or one you rent. Enter its address and port; the page spells out which port and what traffic to forward where on the relay.

After saving, each entry adds a node marked ⇄ to subscriptions, next to the direct node, and clients pick the faster one by latency. To send users through relays only, tick "List only the relay entries in subscriptions, not the exit server's direct node". Every relay node can have its own traffic ratio, speed limits and user capacity under Node settings.

Which exit address it forwards to

A cluster relay forwards to the exit's public IP by default. With a dual-stack exit, is that IPv4 or IPv6? From v0.8.1 the rule is:

  • it follows the IP version this line uses on the exit — if you chose IPv6 for that server under "Deploy to" (or, with no choice there, the server's own setting says IPv6), the relay forwards to its IPv6 as well;
  • provided the relay itself has IPv6; otherwise it stays on IPv4;
  • for Hysteria2 and TUIC lines, a relay that is itself listed by IPv6 in subscriptions also prefers IPv6.

To change it, click the address in parentheses and type another: the other IP version, or a private address when the two servers share a network.

Hysteria2 / TUIC through a relay: connected, but no internet

This is the most common report about relay entries: TCP lines (VLESS, Trojan, AnyTLS) work fine through the same relay, Hysteria2 connects but pages do not load, and connecting to the exit directly is fine.

The likely cause is that the relay-to-exit leg cannot carry large UDP packets. Hysteria2 and TUIC run on QUIC; QUIC packets may not be fragmented on the way, and their size is decided by the two ends — the client and the exit. A relay only moves bytes and cannot change that. If this leg is carrier-NAT IPv4 or tunnelled IPv6, larger UDP packets often do not make it — small ones do, which is why it looks "connected". TCP is unaffected because both TCP ends shrink their segments to fit the path.

What to do, in order:

  1. Click the address in parentheses and switch to the exit's other IP version (IPv4 to IPv6, or back). On a relay whose IPv4 egress is NATed while its IPv6 is native, switching to IPv6 usually fixes it at once.
  2. If that does not help, use the line as an upstream for this line instead: there the relay decrypts and sends again, the two legs are separate connections and each negotiates its own packet size.

There used to be a trap here: a line set to IPv6 on the exit was still forwarded to IPv4 by the relay. From v0.8.1 the relay follows the line's choice.

How device limits see relays

When a user comes in through a relay, the exit sees the relay's address as the source, not the user's device. Counting it as a device would refuse a one-device user who is connected directly and then also connects through the relay; and several users on one relay would all "come from the same IP".

So from v0.8.1 connections that arrive through a relay entry take no device slot, and none from a reseller's device pool; they are still listed among the online IPs, marked with the relay they came through. The flip side: the device limit cannot govern relayed connections — to cap how many people use a relay node, set its User capacity under Node settings.

For relays the exit cannot recognise (traffic arriving over a private network, a relay whose inbound and outbound IPs differ, an address entered as a domain), fill in Source IPs seen by the exit on that node; otherwise it is still counted as one device.

Small print

  • Relay nodes do not do port hopping.
  • Traffic is billed to users at the exit server's ratio. If a server has a traffic allowance of its own, what it relays counts toward it as well — the relay and the exit each count the real bytes that pass through them.
  • If the port on the relay is already held by your own realm or gost, the panel asks that server when you enter the port and tells you. If that is exactly the forwarding you set up for this line, switch "who forwards" to the existing-forwarder option: the panel leaves the port alone and only writes the entry into subscriptions.
  • Deleting a server removes the relay entries that go through it or forward to it.
