Backup and server migration with m-ui

Because m-ui keeps everything in one SQLite file and one certificate directory, a backup is one zip and a migration is "restore that zip somewhere else". This is how to do both so that no user has to re-import anything.

What a backup contains

  • The database, checkpointed first so the WAL is folded in and the copy is consistent: lines, upstreams, users with credentials, plans, resellers, nodes, settings, statistics.
  • Certificate files: your issued or self-signed certificate and key, so TLS keeps working after a restore.

It does not contain the m-ui binary (the installer provides that) or anything outside /etc/m-ui. A backup is therefore small — usually a few megabytes — and portable between architectures.

Taking one

Backup → Download gives you the zip now. Scheduled backups run daily at the hour you choose in the panel's time zone, keep a rotation, and can be pushed to Telegram so a copy lives off the server. The file is created with owner-only permissions; it contains every user's credentials, so treat it accordingly.

Restoring

Two ways, same result:

  1. From the panel: Backup → Restore, upload the zip. m-ui inspects it, shows what is inside, then swaps the database and certificates in and restarts itself.
  2. From the installer: bash install.sh --restore backup.zip on a fresh server installs m-ui and restores in one go — useful when the old panel is already gone.

Either way the restore is atomic: the old database is replaced only after the new one has been validated and copied into place.

Migrating to a new server

The order matters, because subscriptions point at a name or address and clients cache it:

  1. Install m-ui on the new server and restore the latest backup. Ports, panel path, credentials and subscription addresses are now identical to the old server.
  2. Open the new panel and check the dashboard: data plane running, lines listening, users present. The migration wizard on the Backup page walks through exactly this.
  3. If you use a domain, point it at the new server. The wizard can query the major public resolvers so you can watch the change propagate. If you use an IP, edit the server's address on the Servers page — subscriptions update on the client's next refresh.
  4. Nodes need nothing: the master contacts them, not the other way round, and their tokens travelled with the database.
  5. Turn the old server off once traffic has moved. Nothing on clients changed: same credentials, same ports, same subscription link.

Things that are easy to forget

  • Open the same ports on the new server's firewall: the panel, the subscription server, every line, and UDP for Hysteria2 / TUIC.
  • If the certificate was issued for a domain, it works on the new server unchanged; if it was self-signed for the old IP, self-sign again on the new one.
  • WARP is a per-server installation, not part of the backup. Re-run it from the Ops page if you used it.
  • Keep the last backup from the old server until you have watched the new one for a day.

Coming from a legacy panel instead

That is a different tool: the importer reads a compatible legacy panel database and maps inbounds to lines, outbounds to upstreams and clients to users, keeping ports and credentials. Run the installer with --import old.db or use Users → Import for users only; the report tells you what was mapped and what was skipped.
