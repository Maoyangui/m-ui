A checksum is not enough: why updates are signed

A panel that updates itself hands the question "which program gets installed on this server" to its update flow. Before v0.8.1, m-ui downloaded the package and compared it with SHA256SUMS from the same release. That catches a broken download. It does not catch a swapped one: whoever can replace the package can replace the list.

The missing link

A checksum answers "does this file match that list?". It does not answer "who wrote that list?". The package and the list travel the same road: the same domain, the same download, the same proxy or mirror that might be hijacked. An anchor outside that road has to be something that was already on the machine and that nobody on the road can change — the publisher's public key, built into the program.

What gets signed

On every release the publisher's private key (Ed25519) signs the SHA256SUMS file itself. The list holds the SHA256 of every package in the release, so signing the list vouches for each of them. The signature comes in two encodings, both made with the same key:

  • SHA256SUMS.sig: the 64-byte signature in base64. The in-panel updater uses it, and so does the install script when only OpenSSL is available.
  • SHA256SUMS.sshsig: the SSH signature format, verifiable with the system's own ssh-keygen -Y verify — nothing extra to install.

Who verifies, and when

  • The one-click update in the panel, and m-ui update: fetch the list and its signature first and verify with the built-in key; only then look up this architecture's SHA256 in the list, download, compare, replace the program and restart. A mismatch at any step ends it there: nothing is installed, the running program is untouched, and the page says why.
  • The install script: for v0.8.1 and later both signature files must be retrievable, otherwise it aborts. With OpenSSH 8.1 or newer it verifies through ssh-keygen, otherwise through OpenSSL 3; on old systems that have neither it says so and falls back to the SHA256 comparison (updates from inside the panel are unaffected — the program verifies by itself).
  • Before publishing: after signing, the release workflow verifies the result with the freshly built binary and with the install script, then flips one byte of the list and confirms that verification fails — only then does it publish. A tag without the signing key, or a failed self-check, publishes nothing.

Verify one yourself

Download the package, SHA256SUMS and SHA256SUMS.sshsig from the release page into one directory:

echo 'm-ui-release ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIApvcuQzwhE4aH+lWEisKYQnKMJRWsi1Z4idd3DFsCru' > allowed_signers
ssh-keygen -Y verify -f allowed_signers -I m-ui-release -n m-ui-release -s SHA256SUMS.sshsig < SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS

The second line confirms the list was signed by the publisher; the third confirms the package matches the list. Both must pass. The install script can do the second line for you — bash install.sh --verify-sums SHA256SUMS SHA256SUMS.sshsig SHA256SUMS.sig — and on a machine that runs m-ui there is m-ui verify-release SHA256SUMS SHA256SUMS.sig, which uses the key built into the binary.

Upgrading from an older version

Nothing to prepare. v0.8.0 and earlier cannot verify signatures; they keep fetching just the package and the list — both unchanged in signed releases — so they upgrade straight to v0.8.1. From then on every update is verified first. In other words, only the one hop from a version that cannot verify relies on HTTPS and the checksum, exactly as before.

What it does not protect against

  • A compromised release process. A signature proves the list was signed by whoever holds the private key. If the key leaks, or someone controls the release workflow, the signature is still "valid". What it stops is a swap on the download path, or release files being replaced.
  • Packages you supply yourself. With bash install.sh ./m-ui-linux-amd64.tar.gz, or any other download URL, the script fetches no list and checks no signature — the source is your responsibility; verify it as shown above.
  • Key rotation. The built-in keys are a list, so old and new can coexist for a while when the key changes; a very old version, however, only knows the keys it shipped with.
