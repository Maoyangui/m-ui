Which encryption fits which protocol: 73 combinations, tested

A line in m-ui has one of three encryption modes: certificate, Reality or none. Until now every protocol offered all three, and all of them could be saved. After a report that Hysteria2 with Reality saves but never connects, we ran every combination on real servers. The result was worse than "does not connect".

How we tested

Ten protocols × three encryption modes, times five transports for VLESS / VMess / Trojan (TCP, ws, gRPC, HTTPUpgrade, HTTP), plus seven Shadowsocks methods: 73 combinations. For each one, on a real server:

  1. create the line through the panel API and record whether it saved and what it said;
  2. create a user assigned to that line only, wait for the data plane to reload, check whether the port is listening;
  3. fetch that user's three subscription formats (share links, Clash, sing-box);
  4. take the node from the sing-box subscription and connect with a sing-box client, downloading 50 KB;
  5. delete the line and the user, confirm the data plane recovered, move on.

Outcome: 44 connect, 8 are rejected on save, and 21 save but cannot be used. Those 21 fall into four groups.

In one line: Reality goes with VLESS and Trojan only; the two QUIC protocols take a certificate (self-signed is fine); VMess and HTTP take a certificate or nothing.

Group 1: cannot start, and takes other lines down

Hysteria2 and TUIC run over QUIC (UDP). sing-box implements Reality for TLS over TCP only; when the QUIC listener asks it for a standard TLS config, the answer is unsupported usage for reality.

The trouble is how late that error shows up. Before saving, the panel hands the whole config to the core for a dry run (see validation and rollback), but a dry run only constructs the parts, it does not start them, and this error appears when the inbound starts. So:

  • the line saves and the panel says "saved";
  • the data plane reloads with it, fails to start and rolls back to the previous config: every user on that server reconnects, and the new port never opens;
  • the line stays in the database, so any later change to any line meets the same fate: restart, fail, roll back;
  • once the panel service itself restarts (an upgrade, a reboot) there is no previous config to return to: no line on that server starts, and the health check answers 503 from then on.

We reproduced the last point exactly on a test server: a healthy VLESS + Reality line serving traffic, a Hysteria2 + Reality line saved next to it, a service restart, and the healthy line's port stops listening.

Group 2: the inbound starts, the subscription cannot describe it

AnyTLS, VMess and HTTP with Reality are fine on the core side, and the port listens. The problem is the client: share links for these protocols have no way to express Reality (neither anytls:// nor v2rayN's vmess:// has a place for the public key and short ID), so the panel can only write the link as plain TLS, and a client using it against a Reality inbound always fails the handshake. Mixed with TLS is the same story: the nodes in the subscription are written without it.

Someone writing client configs by hand can make such a line work. But when a panel's own subscription cannot connect to the panel's own line, the combination should not be on offer.

Group 3: the combination is fine, the subscription was wrong

VMess with a self-signed certificate: the node in the sing-box subscription fails certificate verification, while Trojan and VLESS with the same certificate connect. The panel could not read its own writing: it wrote "allow insecure" into the vmess link under the key insecure (the one v2rayN reads), but the sing-box subscription is built by parsing that link back into an outbound, and the parser only knew allowInsecure. Not a combination to block, a bug, fixed in v0.8.2: both keys are read, and only a true value counts (before, allowInsecure: false was taken as "allowed").

Tested only with real certificates, this would never show up. That is what connecting through every combination buys you.

Group 4: selectable, never saveable

The Shadowsocks methods 2022-blake3-chacha20-poly1305 and none. Inbounds in the panel are always multi-user (one password per user), and the multi-user 2022 implementation in sing-box supports the two AES methods only; anything else returns invalid argument, and none is not supported with several users either. The dry run rejected them on save, but with the core's own words, which do not tell you what to do. v0.8.2 removes both from the list.

Saveable, but picky about clients

  • Reality with ws / HTTP: sing-box based clients connect (tested). Clients on Xray cores do not; their config check says REALITY only supports RAW, XHTTP and gRPC for now. Use TCP or gRPC if you need both.
  • HTTPUpgrade: clients on recent Xray cores cannot connect; mihomo and sing-box based ones can.
  • Trojan with no encryption: Trojan nodes in the subscription always connect with TLS, so a direct connection fails; behind a CDN or reverse proxy that terminates TLS it works.

These three are not blocked; the form shows a one-line note when you pick them.

What v0.8.2 does

  • When you pick: the three modes always sit side by side; the ones that do not fit the protocol are greyed out. Hover or click one and the reason appears underneath.
  • On save and on enable: the backend checks the same table again (API calls included) and the error names the protocol and says what to choose.
  • Lines already stored: a QUIC protocol with Reality is skipped at render time: no inbound, not in subscriptions, other lines unaffected, and the list marks it "Invalid combo". Upgrading from a version that still holds such a line brings the data plane back by itself.
  • The frontend and the backend each keep a table, and a test compares them; another test pins the core's behaviour (dry run passes, start fails, a certificate starts). The day sing-box supports Reality over QUIC, that test fails and tells us to lift the block.

If you write sing-box configs yourself

  • A passing sing-box check does not mean it starts. Listening ports, TLS for QUIC and certificate files are only settled at start; after a change, look for errors beginning with start inbound in the log.
  • No domain: VLESS + Reality for TCP, Hysteria2 with a self-signed certificate for UDP. Do not try to combine the two.
  • One misconfigured inbound stops the whole process, not just itself. That is why the panel treats each line as something it can drop on its own.
