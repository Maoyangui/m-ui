# m-ui 架构

> 本文按"现在真实跑着的代码"写,不是愿景稿。每节末尾的 **实测** 指在 JP(testw.joinvip.vip)/ HK 两台真机上验证过的行为。

## 1. 目标与边界

m-ui 要解决的是一个人管两到三台入口服务器、几十到几百个订阅用户的场景:

| 需求(用户原话) | 落点 |
|---|---|
| 面板内输入域名申请证书;各机各签 | 证书页(ACME http-01 / Cloudflare dns-01),自动续期,热更新 |
| 一键开关 WARP 本地代理;vps.txt 里的优化全部进面板 | 运维页(WARP 安装/启用/停用/卸载、swap/sysctl+BBR/limits/NTP,参数可调) |
| 双服务器,只管一台;用户/出站/路由/流量/日期全同步 | Hub/Agent:主机推快照、回收账本、集中判定 |
| 入站按延迟自适应;clash 为主,Shadowrocket 多 | 订阅按服务器展开节点 + 每线路 url-test 组,客户端选延迟低的入口 |
| 定期换机,一键还原全部状态 | 单 zip 备份(库 + 证书),上传即整机还原自动重启;换机向导 |
| 单用户同时在线设备数、上下行限速 | 数据面 Limiter:按源 IP 并发计数(跨机并集)+ 令牌桶 |
| 角色开关:关=主,开=副 | 设置 `nodeMode` 一个布尔 |
| 从旧面板备份无缝迁移 | importer:端口/凭据/面板路径/订阅 URL 全保留 |

**不做的事**:多租户、复杂路由规则(域名/GeoIP 分流交给客户端)、多协议链式代理、Web 终端。

## 2. 一张图

```
                     ┌──────────────────────── 主机 (HK) ────────────────────────┐
  浏览器 ──HTTPS──▶  │ web  ──▶ runner ──▶ core(内嵌 sing-box) ──▶ 上游/直连/WARP │
  客户端 ─订阅────▶  │ sub                  ▲   ▲                                  │
                     │ jobs(收账/执法) ─────┘   │ hub(每 5s)                       │
                     │ monitor(巡检/告警)       │   │ 推快照 / 拉报告 / 下发外部 IP │
                     │ acme / backup / ops       │   ▼                              │
                     └────────── SQLite(单文件)──┼──────────────────────────────────┘
                                                 │ HTTPS + X-Agent-Token
                     ┌──────────────────────── 副机 (TW) ────────────────────────┐
                     │ web(agent 接口) ──▶ runner ──▶ core ──▶ 相同上游/本机 WARP  │
                     │ jobs(只收账:AgentCounter 单调账本)                          │
                     └─────────────────────────────────────────────────────────────┘
```

一个二进制、一个 SQLite 文件、一个 systemd 单元。主副机跑同一份代码,行为差异只由 `nodeMode` 决定。

## 3. 数据模型(核心抽象)

- **Line 线路** = 入口协议 + 端口 + TLS/传输 + 上游。渲染成 sing-box 的一个 inbound 和一条 `inbound→outbound` 路由规则。端口在所有服务器上一致,所以"线路"天然就是跨机概念。
- **Upstream 上游** = 一个 sing-box outbound(WARP 就是 socks 127.0.0.1:40000)。`direct`/`block` 内置不入库。
- **User 用户** = 凭据(按协议分键,一次生成全协议可用)+ 配额/到期/周期重置/设备数/限速 + 计量;`UserLine` 决定订阅里有哪些线路。
- **Node 入口服务器** = 域名(订阅里的连接地址与 SNI)+ API 地址 + 令牌;`is_local` 标本机。
- **Plan 套餐** = 上述用户字段的模板。
- **Stats** 时序桶(resource/tag/time/direction 唯一,累加合并)——天然支持多机合并。
- **AgentCounter / TrafficCursor**:副机只增不减的账本 + 主机侧游标,见 §6。
- **Setting** key/value:端口、证书路径、角色、通知、巡检、备份等一切开关。

选择 SQLite(纯 Go 驱动、WAL)的理由:单文件即全部状态,备份 = `VACUUM INTO`,换机 = 复制文件;规模(几百用户、几十线路)远在其舒适区。

## 4. 进程内组件与职责

| 包 | 职责 | 依赖方向 |
|---|---|---|
| `core` | 内嵌 sing-box:Box 生命周期、StatsTracker、ConnTracker、Limiter、入站用户热换、干跑校验、单个出入站增删 | 只依赖 sing-box |
| `render` | DB → sing-box JSON;协议特性表;TLS(cert/reality/none)与传输;上游 outbound | model |
| `runner` | 编排:渲染→启动→**三级重载**;证书签发/续期;备份/重启;首启初始化;暴露给 web/hub 的能力 | core render sub jobs monitor hub notify acme backup |
| `web` | 会话认证、CSRF 守卫、REST API、审计、内嵌前端(零构建 ES modules)、agent 接口 | runner |
| `sub` | 订阅生成(链接/clash)、落地页、订阅服务(独立端口直出 HTTPS) | render model acme |
| `jobs` | 10s 收账、1m 执法(重置/禁用/踢线)、24h 清理 | core model |
| `hub` | 主副机同步(§6) | model notify |
| `monitor` | 上游巡检、看门狗、用户预警、日报 | notify |
| `acme` / `certutil` | LE 签发、证书信息/预检、自签、TLS 热加载 | — |
| `backup` / `ops` / `notify` / `creds` / `importer` | 见名知义 | — |

依赖是单向的:`web → runner → (core, render, …)`;`runner` 通过函数注入把能力给 `jobs/monitor/hub`,避免环。

## 5. 数据面:三级重载

这是 m-ui 最重要的运行时决策——**改什么就动什么,绝不为了小改动断所有用户**:

| 变更 | 动作 | 用户连接 |
|---|---|---|
| 用户增删/启停/配额/限速/线路分配 | `ReloadUsers`:入站用户表原地热换(hy2/anytls/tuic/trojan/vless/vmess/ss),不支持热换的入站(socks/http/mixed)单独重建;被移除的用户即时踢线;限速/设备数策略重下发 | 不受影响(被禁用者除外) |
| 上游增删改、测试 | `ReloadUpstreams`:对比上次应用的出站集合,只对变化的 tag 做 Remove/Add | 不受影响 |
| 线路增删改、线路换上游、证书更换 | `ReloadAll`:先 `ValidateConfig` 干跑新配置,通过才 Stop/Start | 断开一次 |

保存前还有一道 **整配置干跑**:任何线路/上游写入都在事务里渲染整套配置并用 sing-box 初始化一遍,不通过就回滚。这是从真机事故学来的:一条缺 PSK 的 ss2022 线路曾让之后每一次重载都失败。

**实测**:JP 上改上游数据面 uptime 不归零;经 HK 副机 hy2 入站 57ms、ss2022 61ms、经 WARP 16ms。

## 6. 双机同步(Hub ↔ Agent)

- **推**:主机每 5s 构造快照(线路/上游/用户(去掉计量)/用户线路/入口/少量订阅设置)并算修订号;与上次推送不同(或超 10 分钟)就 `POST /api/agent/apply`。副机整表替换(保留自己的账本),按变化类型走三级重载。
- **拉**:同一轮 `GET /api/agent/report` 拿到副机的单调账本、在线 IP、运行状态、证书剩余天数。主机按 `TrafficCursor` 只计增量;计数器变小(副机重装)视为回绕,游标归零重认。增量写入用户与 `Stats`(resource=user 与 resource=node)。
- **判定只在主机**:副机 `jobs` 不执法。主机禁用用户 → 快照变化 → 5s 内推到副机 → 副机热换用户表踢线。
- **设备数跨机**:主机把"其他机器上在线的 IP"下发给每台机器的 Limiter;本机计数 = 本机活跃 IP ∪ 外部 IP,同一 IP 切换入口不占新名额。
- **失联**:>60s 拉不到报告告警一次,恢复再告警一次;副机离线期间主机照常工作,副机继续用最后一份配置服务用户(只是账本回收延后)。

鉴权:`X-Agent-Token` 常量时间比对,非副机角色一律 403;传输建议 HTTPS(副机自签时主机可选跳过校验)。

**实测**:配对 → 3 线路/用户推送 → 禁用传播 → 副机流量回收到主机(up/down 增量)→ 主机看到副机上的在线 IP。

## 7. 订阅

- 入口列表来自 `nodes` 表:多入口时每条线路按入口各出一个节点,名字加 `-入口名` 后缀;单入口不加。
- **节点地址默认是服务器 IP,域名只作 SNI**(设置 `subServerAddr` 可改为域名):大陆客户端本地 DNS 常被污染,Shadowrocket 这类在本机解析域名的客户端会直接超时,而走远程解析的客户端(nextin)不受影响——给 IP 两边都稳,TLS 靠 SNI 照常校验。每台服务器的公网 IP 由本机探测(主机)或随报告上报(副机),也可在服务器页手填。
- 每台服务器有**流量倍率**:经它的流量按倍率计入用户用量(主机本机在收账时乘,副机账本回收时乘,游标记原始值),节点名带 `x2` 标记。
- 线路可选**部署到哪些服务器**(`NodeIds`,空=全部):渲染只含本机应部署的线路,订阅只出对应入口。
- **外部节点**:分享链接或外部订阅 URL,主机定期抓取(通用 UA,base64/明文链接/clash YAML 都能解析,链接→clash 经 sing-box 出站参数中转),分配给用户后追加在本站节点之后、进 Proxy/Auto 组;缓存随快照下发副机,副机订阅口同样可用。
- clash:多入口时每条线路生成 `url-test` 组,`Proxy` 选择组列线路组;`Auto` 覆盖全部。这就是"入站自适应":选择在客户端完成,不需要服务端探测用户延迟。
- 链接订阅:hy2/anytls/ss 与旧面板输出字节级一致(黄金测试),其余协议按 v2ray 风格参数。
- 自签证书(纯 IP)自动带 `insecure`/`skip-cert-verify`,Reality 除外;纯 IP 入口不发 SNI。
- 浏览器打开订阅地址得到落地页(用量/到期/一键导入/二维码);客户端 UA 得到原始订阅。

## 8. 证书、备份与重启

- 证书文件路径固定在设置里;面板与订阅服务用 `GetCertificate` 每 5s 检查文件变化,续期不重启;数据面通过 `ReloadAll` 换证书。
- 备份 = `VACUUM INTO` 一致快照 + 设置引用的证书文件 + meta.json 打 zip。还原分两步:落到 `<db>.restore`,进程原地 `exec` 自身,启动时原子替换(旧库保留 `.bak-时间`),证书写回原绝对路径。Linux 用 `syscall.Exec`,不依赖 systemd 的 Restart 策略。
- 前端资源按内容哈希打 ETag,升级后浏览器立即拿到新文件。

## 9. 安全模型

- 面板:bcrypt 密码、HttpOnly cookie、同 IP 10 分钟 5 次失败告警;写请求校验 `Sec-Fetch-Site`/`Origin` 防 CSRF。
- 两步验证:RFC 6238 TOTP(`totp` 包,SHA-1 / 6 位 / 30 s,±1 步容差);密码正确后才要求验证码,不泄露是否开启;同一时间步的验证码只能用一次(防重放);密钥暂存内存,认证器验证一次成功后才写入 `totpEnabled/totpSecret`;CLI 菜单可关闭(手机丢失兜底)。
- 外部 API(`/api/v1/*`):独立于会话的 Bearer 令牌(64 位十六进制,常量时间比对),`apiEnabled` 关闭即全部 401;写操作审计记为 `api`。令牌与 2FA 设置不随主副机同步。
- 主副机:令牌 + 常量时间比对;快照不含令牌与计量。
- 备份文件含用户凭据与证书私钥——下载/推送 Telegram 前要知道这一点。
- 运维脚本是固定模板,只接受校验后的数字与 `key=value` 行。

## 9.5 诊断

- 概览"最近入站连接":从数据面日志按 源 IP × 线路 聚合。客户端"连不上"先看它:没有客户端 IP = 包没到服务器(端口被封 / DNS 污染 / 客户端配置),有 IP 但不可用 = 协议/证书/密码。
- 上游巡检、副机状态、证书剩余天数、公网 IP 探测都在面板上可见;审计日志记录每一次改动的操作者。

## 10. 失败模式与对策

| 场景 | 行为 |
|---|---|
| 新配置有错 | 保存被拒(整配置干跑);即使漏网,`ReloadAll` 干跑不过就保持旧数据面 |
| 证书未就绪 | 数据面启动失败但面板/订阅继续,方便在面板里解决 |
| 副机失联 | 主机照常,副机用旧配置继续服务,恢复后自动追平 |
| 副机重装 | 账本回绕被识别,不重复计、不漏计 |
| 进程重启 | 所有状态在 SQLite;WAL 每 10 分钟检查点,备份随时可复制 |
| 升级 | 换二进制重启;ETag 让前端不缓存旧模块;数据库自动迁移 |

## 11. 已知边界与下一步

- 线路(入站/路由)变化仍需整体重启:sing-box 的路由规则不能运行时改;线路改动本来就低频。
- 设备数的"跨机"依赖 5s 同步周期,极端情况下两机各放行一台后再收敛。
- 计划中:线路/上游流量图与 Top 用户、sing-box JSON 订阅格式、Telegram 之外的通知渠道、更多入站协议(Naive/ShadowTLS)。
